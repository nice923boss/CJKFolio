# Spike 25 Pre-mortem：ICC 色彩管理下的 RGB → CMYK 轉換

日期：2026-07-26　對應 GAPS #92 (a)(b)　觸發：Owner「安排 RGB → CMYK 色彩轉換」

本 spike 要推翻兩條既有決議，故舉證責任在本輪，不在維持現狀的一方：

- §10 Sprint 76（色票管理）：「**無 RGB→CMYK 自動轉換**，色彩轉換屬印廠 ICC 範疇不做 naive 換算」
- §10 Sprint 137（本次的直接前置）：「不自動轉 CMYK 的理由：色彩轉換要定 profile 與
  rendering intent，選錯會產出**顏色看似正常、印出來卻偏掉**的成品，屬 R2 須先 spike」

兩條反對的都是「**沒有色彩管理的**逐通道換算」。本 spike 問的是換一個前提後結論是否翻轉：
**有 ICC 描述檔、有明定 rendering intent 時，本產品該不該自己做這道轉換。**

## 1. 最可能失敗的方式

轉出來的顏色在螢幕上「看起來合理」，送印卻偏掉，而**本機沒有任何手段能發現**。
色彩正確性的終局裁判是印出來的紙，需要打樣、分光儀與標準光源；本專案一件都沒有。
真正的失敗形態不是「轉錯」，是**在無法驗證的情況下宣稱轉對了**：把一道自己驗不了的
工序內建進送印路徑，使用者從此以為顏色已經被處理好，於是不再送印廠打樣。
Sprint 137 已經替使用者做過一次相反的選擇（轉灰＋說一聲），使用者至少知道色彩沒了。

次要形態，這些本機驗得到：

- 中性灰（R=G=B）經 ICC 轉換後變成四色灰（C、M、Y 皆非零），直接違反 §9「灰階照片
  走單 K」，且把原本 TAC ≤ 100% 的單 K 影像推高到四色相加。
- 轉出的 TAC 超過 §9 的 320〜340%（Japan Color 2001 Coated 的設計總墨量本就是 350%）。
- 目標 profile 取得不到：§9 指定的 Japan Color 2001/2011 Coated 屬 Adobe 散布，
  §10 Sprint 10 已為此繞過一次（OutputIntent 走 ICC registry 名稱免嵌，避開 EULA
  轉嫁義務）。同一道 EULA 這次繞不過：轉換非得有描述檔的實際位元組不可。

## 2. 失敗機率

分兩層，不能混為一談：

| 層 | 機率 | 依據 |
| --- | --- | --- |
| 色彩正確性本機無法終局驗證 | **100%（不是機率，是能力邊界）** | 無打樣、無分光儀、無標準光源，本專案全程如此 |
| 中性灰變四色 | 高（>70%） | 一般 sRGB → CMYK 感知轉換不含黑版保留；黑版保留是 CMYK → CMYK 的機制 |
| TAC 超 320% | 中（約 40%） | 塗布紙 profile 常見設計 TAC 300〜350%，§9 門檻取 320% 保守下限 |
| 無可散布的預設 profile | 高（>70%） | §10 Sprint 10 已認定 Adobe ICC 有 EULA 轉嫁義務 |

## 3. 早期訊號

- 造一張中性灰梯轉過去，量到 C／M／Y 非零
- `ink.image_max_tac` 對轉出影像量到 > 320%
- 兩個 rendering intent（perceptual 與 relative colorimetric）對同一張圖轉出的分量
  差異大，且無客觀依據可決定該用哪個
- 本機 ICC 庫翻不出 Japan Color，只有作業系統夾帶的美規 SWOP

## 4. 對策

1. 只驗機械性質，不宣稱色彩正確性：TAC、中性灰是否守單 K、往返一致性、耗時
2. 目標 profile 一律由使用者提供，不內建（承 §10 Sprint 101 已有的 ICC 選取器，
   且與 X-4 的 DestOutputProfile 同一個檔＝轉換目標與宣告的輸出條件一致）
3. 轉換後強制過既有 `preflight.check_ink_coverage`，超標據實回報不沉默
4. 中性來源（灰階類）不進 ICC 轉換，維持既有單 K 路徑（§9 明文「灰階照片走單 K」）
5. Gate 4 獨立路徑：轉出的 CMYK 進 PDF 後以 PyMuPDF 讀回複量，不採信 PIL 自報

## 5. 放棄條件

- 找不到可散布的預設 CMYK profile ⇒ **不做「自動」轉換**，只做「使用者給了描述檔才轉」，
  且維持 Sprint 137 的轉灰為預設
- 中性灰無法保持單 K 且無可靠機制可保 ⇒ 灰階來源永不進轉換路徑（縮限適用範圍）
- 轉出 TAC 恆超標且無法由 profile 自身的墨量限制吸收 ⇒ 回報並要求使用者換 profile，
  本產品不自行做墨量壓縮（那是另一道需要打樣才驗得了的工序）
- 任何情境下需要「無 profile 時退回 naive 換算」⇒ 直接放棄該情境。Sprint 76 決議
  禁的正是這個，沉默降級比不做更糟

## 6. 替代方案

維持 Sprint 137 現狀：送印路徑轉灰並據實警告，文件明列「先於影像軟體轉 CMYK 再置入」。
此方案的成本是使用者多開一次 Photoshop／Affinity；收益是色彩由有打樣能力的一方負責。

## 7. 預估誤差範圍

探針本身半天（ImageCms 已隨 Pillow 在庫，無新相依）。若結論為「有條件做」，實作面
改動集中在 `pdf_writer._image` 單點與 UI 一個選項，估一個 Sprint；若結論為「不做」，
產出是本報告與 GAPS #92 (a) 的定案回填，估半個 Sprint。真正的不確定性不在工時，
在**驗收**：機械性質驗得完，色彩正確性驗不了，這一點不會因為多花時間而改變。

# Spike 18 Pre-mortem：彩色 CMYK 影像置入

日期：2026-07-18　對應 GAPS #29 (c)（Sprint 50 圖片置入 v1 登記的 Phase 4 剩項）

## 1. 最可能失敗的方式

PIL 讀 CMYK 影像的分量值與 PDF `/DeviceCMYK` 的語意不一致（Adobe 寫的 CMYK JPEG
帶 APP14 標記且分量反相），逕自把 `Image.tobytes()` 寫成影像 XObject，得到**負片
色彩**。更糟的是螢幕 PNG 預覽走另一條路（PIL 自行轉換）看起來正常，缺陷只在送印
的 PDF 裡，人眼在本產品內看不到。

## 2. 失敗機率

高（>50%）。PIL 的 CMYK JPEG 反相是長年已知行為差異，且本產品自寫 PDF 寫出層
（不經任何 PDF 函式庫代為處理色彩），沒有第三方元件會替我們吸收這個差異。

## 3. 早期訊號

- 同一張圖存成 TIFF 與 JPEG 兩種容器，PIL 讀出的分量值不相等
- 寫出的 PDF 經獨立解碼器讀回，分量值與來源檔不符（或呈 255−x 關係）
- 白色區域在 PDF 裡量到高墨值（CMYK 白＝0,0,0,0，反相後為 255,255,255,255）

## 4. 對策

1. 先量測真書送印稿全部影像的色彩空間形態（`tools/measure_cmyk_images.py`），
   確認真實印刷檔採用的形態與是否帶 `/Decode` 反相陣列
2. 抽真書一張 `DeviceCMYK` 影像，存成 TIFF 與 JPEG 兩容器，比對 PIL 讀值
3. 端到端往返：來源檔 → 本產品寫出 PDF → PyMuPDF 獨立解碼讀回像素，逐分量比對
4. 以「白／黑／已知色塊」合成圖做極值檢查（白區必須量到 0,0,0,0）

## 5. 放棄條件

- 往返比對無法對齊到可解釋的關係（既非相等亦非一致反相）→ 停工重議，不出貨
- 需要嵌入 ICC 才能保色（＝ICCBased 色彩空間）→ 與 X-1a `color-cmyk-only`
  規則衝突，改列 GAPS 不做
- 修正反相需對「來源容器」逐一特判（形態不收斂）→ 只支援收斂的容器，其餘拒收

## 6. 替代方案

只接受無容器歧義的來源（CMYK TIFF），JPEG CMYK 直接快速失敗並提示轉檔。
本產品不做 RGB→CMYK 換算（Sprint 76 色票決議：色彩轉換屬印廠 ICC 範疇），
故「使用者自備已轉好的 CMYK 檔」本就是既定分工（§7 對策「影像外部轉 CMYK 置入」）。

## 7. 預估誤差範圍

影像層與 PDF 寫出層改動小（`EmbeddedImage` 依 mode 分流，1〜2 小時）；風險與時間
全集中在反相驗證與兩後端預覽一致性，估半天。
